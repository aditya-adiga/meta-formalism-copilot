## Approach

Build the git half of DD-009's #4' pipeline as additive composition over S1's seam, entirely behind the existing default-off, dev-only flag, with a **transport/logic split** so the CPU-heavy worker stays thin and the git logic stays CI-testable. Five new self-contained modules in `app/lib/corpus/`:

1. **`gitFs.ts`** — a thin **iso-git-fs shim over `CorpusFS`** (the chosen FS route; see decision below). Presents iso-git's required `fs.promises` surface (`readFile/writeFile/unlink/readdir/mkdir/rmdir/stat/lstat`) over the 5-method `CorpusFS`, translating `CorpusFS`'s null-on-missing into the `ENOENT`-coded throws iso-git branches on, and synthesizing directory `stat` (with `isDirectory()`/`isFile()`) from `readdir`.
2. **`gitCore.ts`** — the plain, testable git logic: `init/commit/log/status/push/pull` calling REAL `isomorphic-git` over an INJECTED `{ fs, http, dir, onAuth }`. No worker, no global iso-git http import. `log` takes `{ filepath?, depth, cursor? }` and returns `{ entries, nextCursor }` (lazy pagination — the 3000-commit-cliff mitigation). Conflict → `CorpusError {kind:"git-conflict", path}`; remote-auth (401) → `{kind:"remote-auth-expired"}`.
3. **`gitProtocol.ts`** — the typed worker request/response discriminated union + a plain `handleGitRequest(core, msg)` dispatch that wraps the whole body so ANY throw (typed or not) is reified via `toWorkerError` into `{ ok:false, error: CorpusWorkerError }`; success → `{ ok:true, result }`. No untyped throw ever crosses `postMessage`.
4. **`gitWorker.ts`** — the thin Web Worker entry: `onmessage` → `handleGitRequest` → `postMessage`. Imports iso-git + a worker-scope `Buffer` shim. Untestable in jsdom (covered by smoke). Named `gitWorker.ts` (NOT a reserved App Router filename).
5. **`gitWorkerClient.ts`** — the main-thread `CorpusGit` proxy over an injected transport (`{ post, onMessage }`, a real `Worker` in prod / a fake in tests): correlates requests by id, reconstructs `new CorpusError(error.detail, error.message)` from a `{ok:false}` response and throws it, so callers get a typed `CorpusError` identical to the non-worker path.

Plus a `CorpusGit` **interface** (added to `types.ts`, next to `CorpusFS`, since the seam doc and S1 already document it living there) — SEPARATE from `CorpusFS` (arch-review F1). Tests come first and run against real iso-git on a Node tmpdir (the git logic IS CI-testable since vitest runs on Node) + the in-memory `CorpusFS` fake (the shim); the real worker + real OPFS-backed git + real remote push/pull are documented as an out-of-CI smoke (`docs/spikes/corpus-git-smoke.md`), never claimed as CI-tested.

**Design decisions resolved here** (from research + test-strategy + arch-review):

- **FS route: (a) iso-git-fs shim over `CorpusFS`, NOT (b) lightning-fs.** Chosen for DD-009's OPFS single-substrate mandate — lightning-fs is IndexedDB-backed, which would split the corpus across two substrates (OPFS for `CorpusFS`, IndexedDB for git) and create a reconciliation debt the decomposition does not budget. The shim is ~150 lines and verified by running real iso-git over it. The tradeoff: the shim must implement a broader fs surface than `CorpusFS` (the extra `mkdir`/`rmdir`/`lstat`/dir-`stat`), and the `walkDir` per-op cost (S1 review C3) applies — both acceptable (mkdir is a no-op given CorpusFS's implicit dirs; C3 is the deferred cross-adapter refactor). lightning-fs stays a **documented fallback** if the shim's dir-stat synthesis proves fragile against a real OPFS adapter (a smoke finding would trigger it). *Inspected iso-git@1.38.3's `FileSystem` wrapper (models, index.js:4964) to confirm the exact `promises` surface + `err.code` branching + `normalizeStats` shape before choosing — the shim is viable.*
- **Worker protocol**: a typed discriminated union request (`{ id, type:"init"|"commit"|"log"|"push"|"pull"|"status", args }`) → response (`{ id, ok:true, result } | { id, ok:false, error: CorpusWorkerError }`). The dispatch (`handleGitRequest`) is a plain function CI tests directly; the worker is a 10-line shell.
- **commit-on-write wiring: NOT wired in S3.** Expose a clean `CorpusGit.commit()` for S4 (the session-model rewrite) to call on logical save boundaries. Committing on every blob `writeFile` would create noise commits and couple git to the storage seam; logical save boundaries belong to S4. S3 ships the capability + tests; the trigger is S4. (Documented; arch-review F2/F3 keep it decoupled.)
- **Conflict v1 = per-file last-write-wins + surfaced warning.** S3 implements the detection→`{kind:"git-conflict", path}` typed-error path. The warning UI is S5. No new error kind (the kind already exists).
- **CI remote test depth**: test commit/log/status against a real Node tmpdir, and auth/conflict via injected fakes (401 http; a divergent-clone for conflict). The real push/pull round-trip against GitHub/GitLab is a smoke item (the Node spike measured pack-build only — S3 does not over-claim).
- **No new `CorpusErrorKind`**: `git-conflict` and `remote-auth-expired` already exist in `types.ts` (arch-review F4). `CorpusFS` is NOT widened with git methods (arch-review F1).

## Risks

- **Supply-chain — `isomorphic-git@^1.38.3` is the initiative's FIRST runtime dependency** (folded `dependency-upgrade` lens). It is the spike-validated version; adding it is authorized by DD-009 (the whole spike series validated iso-git) but it is a real ongoing tax (DD-009 §Consequences, §Revisit triggers). Audit: install added iso-git@1.38.3 cleanly; its transitive set is small and well-known (async-lock, clean-git-ref, crc-32, diff3, ignore, minimisted, pify, pako, readable-stream) at ~5.1MB; `npm audit` shows NO new advisories from iso-git (the 2 pre-existing moderate findings are postcss-via-next, unrelated). **Mitigations:** (1) iso-git is contained to two worker-side files behind a flag (arch-review F6) — rip-out blast radius is small; (2) DD-009's revisit trigger (iso-git latest release >12–18 months OR an open critical advisory) governs ongoing health; (3) the version is pinned to the spike-validated `^1.38.3`. **Revisit per DD-009 §Revisit triggers if iso-git stalls (>18mo no release) or a critical CVE lands without a 60-day patch.**
- **The `gitFs` shim's dir-stat synthesis may diverge from real OPFS semantics** — stat-null-but-readdir-nonempty is a heuristic for "is a directory"; under a real OPFS adapter the timing/behavior could differ. Same residual risk class as S1/S2's fake-vs-real; mitigated (not eliminated) by running real iso-git over the shim in CI (G7–G13) and the out-of-CI git smoke (step 11). lightning-fs is the documented fallback if the smoke surfaces a shim defect.
- **The real remote round-trip is unmeasured** — the Node spike measured pack-build only; S3's CI tests auth/conflict via injected fakes. The real GitHub/GitLab push/pull (HTTP transport, wire cost) is a smoke + pre-launch item (carried from both spikes' "what the spike did NOT answer"). S3 does not over-claim.
- **commit-on-write is deferred to S4** — S3 ships the `CorpusGit.commit()` capability but does NOT wire it to corpus writes. Until S4 calls it on logical save boundaries, enabling the flag does not auto-commit. Flagged so it is not mistaken for "the git pipeline is live."
- **Turbopack Buffer wiring is environment-sensitive** — the worker-scope shim is the primary mitigation (no main-bundle polyfill needed); if a Turbopack resolve alias is still required it is one config line. The risk is a build-time surprise, caught by the step-10 `npm run build` gate.
- **C3 (walkDir per-op re-resolution)** carried forward unfixed by design (the shim inherits it) — the deferred cross-adapter perf refactor for when files-per-artifact lands (S4).

## Rollback

This slice ships no user-visible change (flag default-off, production-guarded), so post-ship rollback is low-stakes:

1. `git revert <s3-merge-sha>` — removes the new modules + the `types.ts` `CorpusGit` addition + the `next.config.ts` Buffer line + the `package.json`/lockfile iso-git add atomically. Because the flag is default-off and commit-on-write is not wired (S4), no production data path used git; revert has no data-state consequence.
2. To remove ONLY the dependency without reverting the code: `npm uninstall isomorphic-git buffer` and revert the lockfile — but verify the lockfile fully reverts (a dependency-upgrade gotcha) and re-run `npm test` to confirm the corpus tests skip/guard cleanly.
3. No schema/data migration to undo (S3 introduces none; the `.git/` dir only appears in a dev corpus when the flag is on and git is exercised).
4. **No irreversible component.** The only persistent side effects possible are OPFS/`.git` files written during *dev* testing with the flag on (clear via the browser's site-data) and commits pushed to a *dev-chosen* throwaway remote during smoke testing.
