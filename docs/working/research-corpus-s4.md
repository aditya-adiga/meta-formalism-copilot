# Research: DD-009 corpus S4 — data-model migration + session-model rewrite

- **Goal**: Replace the lossy localStorage session model with the corpus folder layout so the original DD-009 trigger bug — switching workspace sessions silently erases custom-artifact-type references and flattens per-panel version histories — becomes STRUCTURALLY IMPOSSIBLE, and fold the five fragmented localStorage stores into the corpus via a one-shot, backup-before-delete migration.
- **Problem framing**: The session bridge in `app/page.tsx` serializes in-memory state into a flattened `PersistedWorkspace` blob on every session switch; the blob omits `customArtifactTypes`/`customArtifactData` and collapses `ArtifactRecord.versions[]` to a single version, so a switch loses data the store itself holds. **Considered and discarded:** "just call the store's own `getSnapshot`/`resetToSnapshot` (workspaceStore.ts:472-491, which DO include custom types + full `artifacts`) from the session hooks." That would fix the immediate symptom in ~10 lines, but it keeps the blob-snapshot model that makes the data-drift class of bug structurally re-introducible (a future field added to the store but not the snapshot re-creates it), and DD-009 Diamond 1 explicitly reframed the bridge bug as a symptom of the persistence model, not the disease (DD-009 §Context). S4 must make sessions a data-level operation (load a different folder/ref), not a better blob copy.
- **Project state**: branch `feat/corpus-s4-migration` off `integration/6.1` (which integrates S1+S2+S3); the keystone sub-task — depends on S0 layout + S1 adapter, integrates whatever of S2/S3 has landed (both have); blocks nothing downstream except S5's status UI · not blocked (S1 blob-mode seam + paths.ts/manifest.ts + S3 `CorpusGit.commit()` all committed) (cite: docs/working/decomposition-corpus-architecture.md §S4; docs/thoughts/corpus-fs-seam.md §Load-bearing facts).
- **Task status**: research complete; plan drafted and gated (pre-mortem + architecture-review both self-applied); awaiting user approval at the RPI firm gate before any implementation (this sub-task migrates data — the gate is non-negotiable).

## What exists

### The lossy session-snapshot bridge (the bug's mechanism)
Workspace-session switching does **not** use the Zustand store's own `getSnapshot`/`resetToSnapshot` (workspaceStore.ts:472-491, which DO include `customArtifactTypes`, `customArtifactData`, and the full `artifacts` map with all versions). It uses a **separate, lossy bridge** defined in `app/page.tsx` and passed into `useWorkspaceSessions`:

- `getWorkspaceSnapshot()` (`app/page.tsx:124-143`) builds a `PersistedWorkspace` (`version: 2`) that **omits `customArtifactTypes`/`customArtifactData` entirely**, and calls `s.getArtifactContent(key)` per structured artifact (lines 137-141) — `getArtifactContent` resolves only `versions[currentVersionIndex]` (workspaceStore.ts:425, 126-129), so **only the current version survives**; `ArtifactRecord.versions[]` history is flattened away.
- `resetWorkspaceToSnapshot()` (`app/page.tsx:145-173`) rebuilds each artifact as a **single-version record** (`versions: [makeVersion(content, "generated")]`, lines 150-156) and `setState`s a field set (lines 160-171) that **omits `customArtifactTypes`/`customArtifactData`**. Because Zustand `setState` is a partial merge, those two keys are left untouched on the store → custom-type **definitions leak across sessions** (the next session sees the prior session's custom types), while custom-type **generated content** is dropped because nothing carries it through the blob.
- `clearWorkspace()` (`app/page.tsx:175-178`) calls `useWorkspaceStore.getState().clearWorkspace()` (workspaceStore.ts:492, resets to `DEFAULT_STATE`) and returns an empty `PersistedDecomposition`.

These three callbacks are passed to `useWorkspaceSessions` (page.tsx wiring) and invoked by `switchToSession` (useWorkspaceSessions.ts:208), `createNewSession` (line 175), `deleteSession` (lines 237, 241), and the 5s auto-save `saveCurrentSession` (line 147 + interval line 254-261). The store's own `getSnapshot`/`resetToSnapshot` are NOT wired into the session hooks at all — they are dead-ish (used elsewhere only via `getSnapshot`'s signature). DD-009 §Context cites `page.tsx:135-184`; line numbers drifted to 124-178 but the analysis holds exactly.

### The five fragmented localStorage stores
1. **`workspace-zustand-v1`** — main Zustand store (workspaceStore.ts:495). Holds live `WorkspaceState`: sources, semiformal/lean flat fields, versioned `artifacts` (`ArtifactRecord.versions[]`), decomposition, `customArtifactTypes`/`customArtifactData`. Persist storage seam = `resolveWorkspaceStorage` (workspaceStore.ts:499) — debounced localStorage by default, CorpusFS-backed (blob mode) when the flag is on. `skipHydration: true`; `rehydrate()` called in page.tsx:80-85 `useEffect`. `partialize` (workspaceStore.ts:511-526) and `merge`/`coercePersistedState` (workspaceStore.ts:68-119, 504-507) are the field set + validation.
2. **`workspace-sessions-v1`** — workspace-session index + every frozen per-session `PersistedWorkspace` blob (`useWorkspaceSessions.ts:31, 100`; key `WORKSPACE_SESSIONS_KEY` in workspaceSession.ts:4). `WorkspaceSession = {id, title, createdAt, updatedAt, workspace: PersistedWorkspace, formalizationSessions: SessionsState}` (workspaceSession.ts:6-13). Debounced 500ms (useWorkspaceSessions.ts:25, 99-101); auto-saves active session every 5s (lines 254-261); flush-on-unmount (lines 108-115). **This is where the flattened blobs accumulate** — each session's `workspace` field is the output of the lossy `getWorkspaceSnapshot`.
3. **`metaformalism-sessions`** — per-scope formalization session history (`useFormalizationSessions.ts:10`). `SessionsState = {sessions: FormalizationSession[], activeSessionId}` (session.ts:46-49); each `FormalizationSession` has a `scope: {type:"global"} | {type:"node", nodeId, nodeLabel}` (session.ts:4-6), a `runNumber`, deductive fields (semiformalText/leanCode/verification), and a multi-artifact `artifacts: ArtifactData[]` (session.ts:31-44). **Also frozen INSIDE each `WorkspaceSession.formalizationSessions`** (workspaceSession.ts:12) — so per-node run history lives in two places and is snapshotted by the same 5s save.
4. **`evidence-store-v1`** — evidence-search results, `slots` only (evidenceStore.ts:116, 121). Separate Zustand store, own debounced adapter (evidenceStore.ts:20-48), `skipHydration: true`. **Not touched by the session bridge at all** — evidence is global, not per-session.
5. **`workspace-v2`** (legacy `PersistedWorkspace`) — read-only migration source. `migrateFromV2()` (workspaceStore.ts:251-285) pulls it into the Zustand store on first rehydrate if the Zustand key has no `sourceText` (onRehydrateStorage, workspaceStore.ts:528-543). `workspace-v1` auto-migrates to `workspace-v2` via `migrateV1Workspace()` (workspacePersistence.ts:10-31, called from `loadWorkspace()` line 200). Notably `migrateFromV2` DOES carry `customArtifactTypes`/`customArtifactData` (workspaceStore.ts:280-281) — so the v2→zustand path is lossless; only the session bridge is lossy.

### The corpus building blocks S4 composes (all on `integration/6.1`)
- `app/lib/corpus/paths.ts` — DD-009 folder-layout path builders; `workspaceSlug`/`safeSegment` are the single traversal choke point. **`stateBlobPath(name)` (paths.ts:83-85) is the S1 blob-mode namespace under `state/`** — S4 must reconcile this blob into the workspace folders and retire `state/` (paths.ts:71-82 comment is explicit).
- `app/lib/corpus/manifest.ts` — `workspace.json` schema (`WorkspaceManifest`: title, sources[], artifacts[] current-version pointers, customArtifactTypeIds[]) + fail-loud `parseManifest` (throws typed `CorpusError` on malformed/absent — never default-empty).
- `app/lib/corpus/types.ts` — `CorpusFS` (5 async bytes+paths methods) + `CorpusGit` (separate interface: init/commit/log/status/push/pull) + the single `CorpusErrorKind` union + `CorpusError`/`CorpusWorkerError`.
- `app/lib/corpus/storeAdapter.ts` — `resolveWorkspaceStorage(connectedMirror?)` chooses debounced-localStorage (default) vs `createCorpusBackedStorage(resolveCorpusFs(...))`. `resolveCorpusFs` (storeAdapter.ts:92-100) is the focused selection helper — **S4's folder-layout arm is added here, not in the wrapping** (seam doc §storeAdapter).
- `app/lib/corpus/mirrorFs.ts` — `createMirrorCorpusFs` decorator (OPFS primary + FSA mirror, async-with-backoff, truthful `getMirrorStatus()`/`onMirror()` ack).
- `app/lib/corpus/gitWorkerClient.ts` / `gitCore.ts` — `CorpusGit` impl (worker proxy in prod, plain core in CI). **`CorpusGit.commit()` exists but is NOT wired to writes — commit-on-write is S4's to add** (seam doc §S3; plan-corpus-s3.md "commit-on-write is deferred to S4").
- `app/lib/corpus/flag.ts` — `isCorpusEnabled()`, default-off, **production-guarded** (flag.ts:21 refuses in `NODE_ENV==="production"`). The guard comment (flag.ts:18-20) says: remove the production guard ONLY when S4 ships migration and the flag becomes a real rollout knob.

## Invariants (must not break)

- **The localStorage OFF path must stay byte-for-byte until migration runs.** `resolveWorkspaceStorage` flag-OFF returns `createDebouncedLocalStorage` (storeAdapter.ts:110-115); S1's characterization test locks this. S4 must keep the OFF path untouched and only run migration as a one-shot when the flag is turned ON for the first time. A user who never enables the corpus keeps localStorage forever. [observed — storeAdapter.ts:110-115, flag.ts]
- **SSR safety.** Every persisted store renders defaults on the server and hydrates in `useEffect`/`useSyncExternalStore` (`skipHydration: true` workspaceStore.ts:501; `getServerSnapshot→EMPTY_STATE` in both session hooks, useWorkspaceSessions.ts:50-52, useFormalizationSessions.ts:33-35). Any corpus read on the migration/session path must NOT touch `window`/OPFS during render — only inside effects/handlers, or it throws on the server and breaks hydration. [observed]
- **Transient-state sanitization on persist.** `verificationStatus: "verifying"` → `"none"` (workspaceStore.ts:520, `sanitizeVerificationStatus`) and node `"in-progress"` → `"unverified"` (`sanitizeNodeStatus` via `sanitizeDecomposition` workspaceStore.ts:523) before any write, so a reload mid-verify isn't stuck. The corpus write path must preserve this sanitization. [observed]
- **Undo/redo semantics.** `getArtifactContent` returns `versions[currentVersionIndex]`; `MAX_VERSIONS=20` caps history (artifactStore.ts:37); `setArtifactEdited` truncates redo history (workspaceStore.ts:387). The corpus per-version files must round-trip `versions[]` + `currentVersionIndex` so undo/redo survives a session switch and a reload. [observed — workspaceStore.ts:401-435]
- **The formalization-session per-node run history is load-bearing.** `FormalizationSession` carries `scope` (global vs per-decomposition-node), `runNumber`, and a per-artifact-type `artifacts[]` (session.ts:31-49). It is stored both standalone (`metaformalism-sessions`) and nested inside each `WorkspaceSession.formalizationSessions`. Migration must fold BOTH into the corpus without dropping a scope or a run, or per-node "previous runs" UI breaks. [observed — useFormalizationSessions.ts; user MEMORY: recursion/per-node history needs care]
- **The evidence store is global, not per-session.** `evidence-store-v1` is a sibling store the session bridge never touches; S4 migration must carry it without trying to scope it to a workspace (or must decide an explicit scope — see open questions). [observed — evidenceStore.ts]
- **`PersistedWorkspace` is a consumed contract.** `workspacePersistence.ts`, the session blob, `docs/example-workspace.json`, and the export feature depend on its shape. S4 introduces the folder layout but must not break the legacy v2 read path that `migrateFromV2` still needs during migration. [observed — persistence.ts:16-37]
- **`extractedFiles` carries a non-serializable `File?` field** stripped by `JSON.stringify` today (workspaceStore.ts:152, partialize comment 509-510 notes File refs are dropped). Source TEXT is persisted; raw source BYTES are not stored today. The corpus folder layout has `sources/<id>.<ext>` for bytes — but S4 can keep storing extracted text only (matching today's behavior) and defer raw-byte storage, since the bug fix does not require it. Storing bytes is new behavior; flag it as a scope decision, don't silently add it. [observed — research-corpus-architecture.md §Source documents]
- **No reserved Next.js filenames under `app/`.** `layout.ts`/`page.ts`/`route.ts`/`template`/`default`/`loading`/`error`/`not-found` are reserved (seam doc §Gotchas; this is why `paths.ts` exists). Any new corpus module S4 adds must avoid these names. [observed]

## Prior art (the migration patterns to follow)

- **`migrateFromV2()` (workspaceStore.ts:251-285)** is the canonical one-shot conversion pattern: read the old key, build the new shape (versioned artifact records from flat strings, lines 256-266), single `setState`, return success. It is idempotent-by-guard (only runs if the Zustand key has no `sourceText`, onRehydrateStorage lines 533-540). **It carries `customArtifactTypes`/`customArtifactData` correctly (lines 280-281)** — so the v2→corpus folding has a lossless reference. S4's localStorage→corpus migration should mirror this: guard, read all five keys, convert to folder layout, write, mark-done, THEN delete-after-backup. [observed]
- **`migrateV1Workspace()` (workspacePersistence.ts:10-31)** is the back-up-then-rename pattern at the localStorage level: read legacy key, if target already exists just remove legacy, else stamp + write target, then `removeItem(legacy)`. The structural lesson: migration removes the old key only AFTER the new key is written. S4 extends this with an explicit BACKUP step (DD-009 §Consequences mandates backup-before-delete) — write the backup, write the corpus, verify, then delete. [observed]
- **The shared `CorpusFS` contract suite** (`app/lib/corpus/__tests__/corpusFsContract.ts`, `defineCorpusFsContract`) — any new folder-layout reader/writer S4 builds over `CorpusFS` inherits the contract guarantees; S4's tests reuse the in-memory fake (jsdom has no OPFS). [observed — seam doc §Load-bearing facts]
- **`docs/thoughts/page-tsx-refactor.md`** documents that page.tsx historically concentrated session wiring and that pipeline-config callbacks suffer stale-closure bugs — directly relevant because S4 adds the async corpus session-switch path; use refs/current-value passing (the existing `fnsRef`/`stateRef` pattern in useWorkspaceSessions.ts:83-87), not closed-over state. [observed]

## Gotchas

- **Two snapshot mechanisms exist** (store-level `getSnapshot`/`resetToSnapshot` at workspaceStore.ts:472-491 vs the page.tsx lossy bridge at 124-178). A naive "wire the store snapshot into the session hooks" fix is a TEMPTING WRONG TURN — it fixes the symptom but keeps the blob model DD-009 rejected. The plan must NOT do this; it must move sessions to a data-level (folder/ref) operation. [observed — seam doc §S1 gotchas echoes this]
- **The S1 `state/` blob is a SECOND copy of the workspace.** With the flag on today, the store writes the whole persist blob to `state/workspace-zustand-v1.json` (storeAdapter.ts:64-80, `stateBlobPath`). S4 must reconcile this: either migrate localStorage → folder layout directly (bypassing the blob) and retire `state/`, or migrate localStorage → blob → folder. The plan picks one and documents the retirement of `state/`. [observed — paths.ts:71-85]
- **OPFS/IndexedDB "write completed" ≠ persisted to disk.** A migration that writes to OPFS and immediately deletes localStorage could lose data if the OPFS transaction has not actually flushed AND the FSA mirror/remote has not acked. The backup-before-delete must gate the localStorage deletion on a TRUTHFUL ack (mirrorFs `getMirrorStatus()` / a git commit), not the bare OPFS write resolve. [observed — research-corpus-architecture.md §Gotchas; seam doc §Load-bearing facts]
- **Migration triggers from a user gesture / first flag-on run, inside an effect.** Because of SSR safety, migration cannot run at module load; it runs in an effect or a handler after `isCorpusEnabled()` is true and a "migration not yet done" marker is absent. The marker itself lives where the corpus can see it (a corpus file or a localStorage sentinel) so a half-completed migration is detectable on next load. [inferred from SSR invariant + flag.ts]
- **Background-tab throttling** (Chromium ~1Hz after 5 min) means the 5s auto-save and any async migration step in a backgrounded tab is far slower than foreground. A migration started then backgrounded must be resumable, not assumed-atomic. [observed — research-corpus-architecture.md §Gotchas]
- **`customArtifactData` keys are `custom-*` ids; coercion filters non-`custom-` keys** (workspaceStore.ts:104-116). Folder layout puts definitions in `custom-types/<id>.json` and content under `artifacts/custom/<id>/`; the migration must keep definition and content together so the bug (definition-without-content or content-without-definition) cannot recur. [observed]
- **iso-git `git.log` is O(commits-touching-file)** and crosses the 5s budget around ~3000 per-file commits (perf-characteristics). If S4 wires commit-on-write, version history that previously lived in `versions[]` now also accrues git commits; the history UI must page (`CorpusGit.log` already takes `{depth,cursor}`), and commit-on-write must batch (one commit per logical save boundary, not per keystroke). [observed — seam doc §S3]
